Blog 2 长时 Agent 的 Harness — 解决"换班"问题

Effective harnesses for long-running agents（2025.11）— 首次使用 "Harness" 术语

核心问题：任务太大，一个上下文窗口装不下，Agent 需要跨多个 session 工作
就像换班工人没有交接信息 — 下一个人不知道上一个人做了什么

两个失败模式：

过度野心

一次做太多，上下文用完时功能半成品 — 没文档、没测试、没提交

过早完成

后续 Agent 看到已有进度，草草检查就宣布"完成了"，实际有 bug

V1 解法：Initializer + Coding Agent

Initializer（只跑一次）

建功能列表 → 创初始化脚本 → 写进度日志 → git commit

Coding Agent（每次 session）

读 git log → 跑测试 → 一次只做一个功能 → 提交 → 更新进度

核心原则：通过文件系统和 git 传递上下文，让每个 session 之间有"交接班"
即使不做长时任务，"一次只做一件事" + "通过文件传递状态"同样适用于日常开发

Blog 3 三 Agent 架构 — 从做完到做好

Harness design for long-running application development（2026.03）

核心升级：GAN-inspired 三 Agent 架构 — 生成与评估对抗，逼出更高质量

Planner 规划器

输入：1-4 句话的简单需求
输出：完整产品规格

只约束"交付什么"，不约束"怎么做"

Generator 生成器

按 Sprint 逐个实现功能
每个 Sprint 结束先自评再交给 Evaluator

有 git 版本控制

Evaluator 评估器

用 Playwright MCP 实际操作应用
逐项打分，低于阈值 → Sprint 失败

返回 bug 描述 + 修复建议

Sprint Contract：Generator 和 Evaluator 在每个 Sprint 开始前"谈判"一份合约 — 商定做什么、怎么算完成

Blog 3 三个关键发现

Context Anxiety

模型接近上下文极限时会过早收尾 — 不是做完了，是"焦虑"了

解法：Context Reset（全新 Agent + 结构化交接）
比 Compaction 有效，因为压缩不消除焦虑感

自我评价偏高

"发现了真实 bug，说服自己不是大问题，放行了"

解法：分离 Generator 和 Evaluator
独立 Agent 评价比自评可靠得多

Evaluator 需要调教

开箱即用的模型是很差的 QA Agent

调教 Evaluator 变严格
比让 Generator 自己变严格容易得多

Blog 3 成本反转 — 贯穿全文的底层逻辑

"how to maximize our one truly scarce resource: human time and attention."
传统模式Agent-first 模式
代码编写昂贵（人力密集）廉价（Agent 批量生产）
纠错/重做需要谨慎避免廉价（Agent 快速迭代修复）
人类注意力充足（人就是干活的）唯一真正的瓶颈
等待/阻塞可接受极其昂贵（浪费 Agent 吞吐量）
QA 验证人力可覆盖人力成为瓶颈，必须让 Agent 自己做
架构约束可以推迟到团队变大前置条件（没有约束 Agent 快速制造混乱）
"corrections are cheap, and waiting is expensive."
这个反转驱动了 OpenAI 几乎所有的工程决策：QA 从人转给 Agent · 合并门控从严变松 · 架构约束从可选变为必须 · Review 从人做变为 Agent-to-Agent · "垃圾回收"自动化

理解了这个反转，才能理解后续所有实践的"为什么" — 全部是为了最小化人类注意力的消耗

Blog 3 上下文管理 — 给 Agent 地图，而非千页手册

"一个巨大的 AGENTS.md" 失败了：

  • 上下文是稀缺资源 — 巨大指令挤占代码空间
  • 太多指导 = 没有指导 — Agent 局部模式匹配
  • 瞬间腐化 — 变成陈旧规则的坟场
  • 难以验证 — 无法做机械化检查

正确做法：AGENTS.md 是目录表

AGENTS.md          ← ~100 行目录
ARCHITECTURE.md    ← 顶层架构
docs/
├── design-docs/   ← 设计文档（有验证状态）
├── exec-plans/    ← 执行计划（一等公民）
├── references/    ← 外部参考（LLM 友好格式）
├── QUALITY_SCORE.md  ← 每个领域/架构层的质量评分
└── ...
三个关键实践： 渐进式披露（从入口到深层信息） · 执行计划是一等公民（提交到仓库，版本化） · doc-gardening Agent（定期扫描陈旧文档，自动 PR 修复）

关键 Takeaways

  • 1. 瓶颈不是智能，是基础设施
    OpenAI、Anthropic、DeepMind 独立得出相同结论 — 模型失败时，修环境而非换模型
  • 2. 成本反转改变一切
    代码编写和纠错变廉价，人类注意力成为唯一瓶颈 — "corrections are cheap, waiting is expensive"
  • 3. 文档结构决定 Agent 效率
    AGENTS.md 是目录而非百科 · 渐进式披露 · 执行计划是一等公民 · 决策落到仓库里

    从文档约束提升为 linter 约束 · lint 错误 = 修复指令 · 分离 Generator 和 Evaluator
  • 5. 小模型 + 好 Harness > 大模型裸奔
    AutoHarness 证实 · Anthropic V2→V3 验证 · Harness 的 ROI 远高于换模型
  • 6. 从简单开始，持续演进
    先 Skills + 验证（P0），再逐步增加复杂度 — 每次模型升级重新审视 Harness

Coding Agent 正在重塑 EPD

当 Agent 真的能写代码了，我们的角色会变成什么？

— Harrison Chase (LangChain CEO), 2026.03.10

三个流程变革

1. PRD 已死

传统瀑布式流程 想法 → PRD → Mock → Code 终结了

分工的前提是"实现需要大量时间"，Agent 打碎了这个前提

2. 瓶颈从实现转向 Review

任何人都能写代码 → 原型数量爆炸 → Review 成为三个职能中的共同瓶颈

Engineering架构可扩展、高性能、鲁棒
Product真正解决用户痛点
Design界面易用、直觉化

3. PRD 万岁 — 意图沟通永在

PRD 流程死了，但意图沟通依然必须。未来 PRD 可能是结构化的 Prompt

EPD 分化为两种角色原型

Builder（构建者）

  • Product thinking + Coding Agent + Design 直觉
  • 小功能从想法到生产，大功能出原型
  • Engineer: 培养 Product/Design 能力
  • PM/Designer: 拥抱 Coding Agent
VS

Reviewer（审查者）

  • 领域极深的系统思维
  • 高速 review 大量 Agent 产出
  • Engineer: 精通系统设计和架构
  • PM/Designer: 极强的心智模型
关键是做有意识的选择 — 而不是被动等待角色被重新定义

判断该做什么（前置）+ 判断做得对不对（后置）

③ 每个人都需要 Product Sense

有 → 最小化 spec，加速沟通
没有 → 你在给组织制造 review 垃圾

④ 通才比以往更有价值

一个通才 > 三个专才团队
（省去沟通开销）

好 PM 更强了，差 PM 更可怕了 — 差的原型比没有原型更危险

Agent 的能力上限不取决于模型本身，
而取决于你如何 harness 它。

而你的价值，取决于你如何 harness 自己。
